## Фаза 0 — гигиена и быстрые правки

Независимые дела, каждое на вечер. Ничего не блокирует, эффект сразу.

**Состояние выката на 04.09.** Код развёрнут и на тестовом узле, и на боевом
бридже: `/opt/groxy` на `moscow-1000-01` переключён на эту ветку (коммит
`c90790c`), `main` не тронут. На тестовом узле поведение проверено на живом
интерфейсе — синхронизация сохраняет сессии и счётчики, конфиг поднимается,
`PostUp` ставит клэмп в `mangle` и не создаёт дубля при повторном подъёме.

На проде выполнено только чтение плюс перерендер `wg0.conf`: 36 пиров до и
после, набор публичных ключей не изменился, интерфейс не перезапускался.
Единственное содержательное отличие нового файла — блок MSS-клэмпа, которого
там не было; теперь перезагрузка бриджа поставит его сама.

`groxy apply` на проде **не запускался**: он перезапускает `wg1`, а это
несколько секунд без зарубежного трафика у всех 36 клиентов. Это работа под
объявленное окно, а не попутная.

**На проде:**

- [x] **Починить резолв DNS на стороне выхода** — выкачено на прод 04.09.
      Akamai видит теперь амстердамскую подсеть вместо московской, узел Steam
      стал 4 мс вместо 138,5, TLS 52–59 мс вместо 163–314. Российская половина
      цела. Замеры до и после — в `DNS-BASELINE.md`, разбор причины — в
      `DIAG-SLOW-STEAM.md`.
- [x] **Поднять `nf_conntrack_max` на `nether`** — сделано 03.09, с 8192 до
      65536 вместе с хеш-таблицей, применено и закреплено. 8192 оказалось не
      чьей-то ошибкой, а значением, выведенным ядром из 960 МБ памяти узла; у
      `sweden` с его 3,9 ГБ уже стояло 65536. Ёмкость описана в коде и ставится
      из `init` и `apply` обеих ролей.
- [x] **Занести MSS-клэмп в репозиторий** — сделано, причём со второй попытки:
      правило записывалось в таблицу `filter`, тогда как на проде оно живёт в
      `mangle` (20 млн пакетов через него, `filter FORWARD` пуст).

**В CLI — предусловия для бота:**

- [x] **Убрать перезапуск `wg0` при добавлении и удалении клиента** — сделано.
      Вместо `wg syncconf` через подстановку процесса используется файл с
      проверками: подстановка скрывала код возврата `wg-quick strip`, а пустой
      конфиг для `syncconf` — не пустая операция, а полное стирание пиров

- [x] **Добавить `flock`** — сделано, и не только в двух командах: блокировку

      перестраивает `ru_cidrs` через общий временный набор и потому конфликтует

- [x] **Сделать команды идемпотентными.** `remove-client` несуществующего —

- [x] **Добавить `--json`** к командам, которые нужны боту.

## Фаза 1 — бот и локальная наблюдаемость

Основная работа. Дизайн и обоснования — в `BOT-DESIGN.md`.

**На бридже:**

- [ ] **Выход бота в Telegram через портал.** Пометка исходящего трафика по uid
      в `mangle OUTPUT`, дальше существующее правило `fwmark 0x1 → vpn2 → wg1`.
      Правило аддитивное, клиентов не задевает.
- [ ] **Бот**, доступ только по списку разрешённых chat_id. Функции: список
      профилей с онлайн-статусом, сводная статистика, статистика по профилю,
      добавить, удалить, переименовать, выдать конфиг и QR (семантика
      перевыпуска).
- [ ] **Снимок раз в минуту в sqlite**, хранение неделю: по пирам — трафик,
      возраст handshake, endpoint; по узлу — CPU, память, диск; по `wg1` —
      потери и скорость.
- [ ] **Накопление сумм трафика поверх счётчиков ядра**, чтобы переживать
      обнуление при перезагрузке.
- [ ] **Доставка алертов с фейловером:** прямо, затем через основной портал,
      затем через резервный. Отдельный алерт на переход к запасному пути.

**На порталах:**

- [ ] **Reporter** — отдаёт память, CPU, диск, conntrack и скорость на
      интерфейсах. Слушает **только на туннельном адресе**, снаружи недоступен.
      Пропускная способность важна отдельно: через портал идёт весь зарубежный
      трафик, упереться в неё реальнее, чем в процессор.
- [ ] **Watchdog** — ждёт периодический пинг от бота, кричит в Telegram, если
      тот замолчал. Закрывает случай «бридж лёг вместе с ботом».

**Алерты, из накопленного опыта:**

протух handshake с порталом; dnsmasq не слушает на `wg0`; список доменов пуст
после обновления; узел или портал недоступен; CPU, память или диск за порогом;
conntrack подходит к потолку; скорость на портале у потолка; рост потерь на
`wg1`; клиент не подключался N дней; handshake рвётся чаще нормы; доставка
алертов ушла на запасной путь.

Живость проверять **независимо от туннеля** — публичной пробой, иначе падение
туннеля неотличимо от падения узла. Матрица разбора — в `BOT-DESIGN.md`.

Критерий: видно каждого клиента и каждый узел, о поломке приходит уведомление
раньше жалобы, и понятно, что именно сломалось.

## Даунтайм

Сам туннель `wg0` не перезапускается нигде, кроме отмеченного места, поэтому
клиентам не нужно ничего переподключать.

| Работа | Кого задевает | Сколько |
|---|---|---|
| Убрать дубль `moscow-test` со `sweden` | никого — прод идёт через `nether` | ~2 с на резервном туннеле |
| Починить резолв DNS | всех: перезапуск dnsmasq | секунды |
| `nf_conntrack_max` | никого | 0, применяется на лету |
| MSS-клэмп в репозиторий | никого | 0 |
| Убрать перезапуск `wg0` при add/remove | никого — **устраняет** текущие обрывы | 0 |
| Фаза 1 целиком | никого | 0 |
| Фаза 2, боевая проверка фейловера | всех: рвутся соединения через портал | 5–15 с, дважды |
| Фаза 3, перевод прода на Xray | всех: рвутся соединения через портал | реально 1–2 мин, окно на 30 |
| Фазы 4 и 5 | никого | 0 |

Сегодня **каждый выпуск профиля** роняет туннель у всех — до правки с
`wg syncconf` регулярный даунтайм уже есть, просто короткий.

Объявлять клиентам стоит две работы: боевую проверку фейловера и перевод прода
на Xray. Окна брать по низкой нагрузке.

Отдельно для администратора: связь с внешним миром идёт через портал, поэтому
Фазы 2 и 3 обрывают собственную рабочую сессию — переключаться на независимый
туннель заранее.

## Зависимости

Фаза 0 не зависит ни от чего, но её правки в CLI (`syncconf`, `flock`,
идемпотентность, `--json`) — предусловие Фазы 1. Фаза 2 требует Фазы 1. Фазы 3
и 5 независимы. Фаза 4 требует Фазы 1.

## Что осталось за рамками

Замена портала на машину помощнее — отдельный трек, по данным Фазы 1 станет
видно, нужна ли. Перекрёстные пробы между узлами и внешний dead-man's switch —
план, не первая итерация. Устойчивость к ТСПУ и Reality сняты с повестки.
Клиентский mihomo — отдельно. Квоты по трафику, сроки профилей, выбор
гео-выхода и ротация ключей — не требуются.
