# Рекомендация: что делать с groxy

Дата: 2026-09-02. Написано после стенда, сравнения протоколов и диагностики
жалоб. Заменяет курс, заданный в `V2-ROADMAP.md` §2 и уточнённый в
`PLAN-3XUI-FORK.md`.

## Требования, как они сформулированы

Обязательное:

1. Маршрутизация по домену, а не по IP.
2. Метрики по клиентам для диагностики: кто сколько потребил, почему подвисало
   в конкретный момент.
3. Админка для добавления клиентов без ручного SSH.
4. Алерты.
5. Автоматическое переключение портала с уведомлением в Telegram.
6. **ICMP должен проходить весь.**
7. Валидация фида до применения, автобэкап с проверкой восстановления, dry-run.
8. Починить резолв DNS не там, откуда выходит трафик.

Желательное:

9. Самообслуживание клиентов в боте: админ выдаёт доступ, человек сам создаёт
   профили в пределах лимита **по количеству** и смотрит свою статистику.

Снято с повестки: квоты по трафику, устойчивость к ТСПУ, узкое место портала
(отдельным треком), клиентский mihomo (отдельно).

## Вывод: панель не берём

Требование 6 решает развилку. Полный L3 даёт только ядерный datapath —
измерено: из туннеля панели `ping 1.1.1.1` даёт 100% потерь, из ядерного
WireGuard проходит за 68 мс. Значит клиенты остаются на ядерном WireGuard, как
в v1 сегодня.

Дальше выясняется, что и панель поверх этого не нужна:

- Требование 2 она не закрывает. Панель хранит текущие суммы по клиенту, а не
  историю. «Почему подвисало в 21:30» требует временных рядов, то есть
  Prometheus в любом случае.
- Требование 9 она тоже не закрывает. В ванильном боте клиент видит свой
  трафик, ссылки и QR, но **сам профиль не создаёт**. Значит свой бот пишем в
  любом случае.
- Требование 4 при ядерном датаплейне она видит плохо: её health-чеки следят за
  собственным Xray, а не за нашим `wg0`.

Остаётся веб-интерфейс для добавления клиентов. Ради одной функции — отдельный
процесс с публичным веб-портом, своя БД, апгрейд-дорожка и агент-прослойка,
которая изображает перед панелью датаплейн, которым та не управляет. Плюс
собственный опыт: 26 августа наша сборка панели ушла в креш-луп на десять
перезапусков подряд.

Требование 3 закрывается ботом: добавление клиента командой в Telegram — это и
есть «быстро и без SSH». А смотреть на парк удобнее в Grafana, которая нужна
для требования 2.

## Целевая архитектура

```
Клиент — обычный WireGuard, конфиг не меняется
   │
   ▼
 wg0 (ядро)
   │
 nftables mangle на бридже:
   tcp/udp  → TPROXY → Xray :12345
   остальное → метка 1 → таблица vpn2 → wg1
   │
   ▼
 Xray: dokodemo-инбаунд, sniffing SNI / Host / QUIC
   │
 правила по доменам:
   RU и carve-out      → outbound "direct"  (freedom без метки, выход с RU IP)
   foreign-denylist    → outbound "portal"
   всё остальное       → outbound "portal"  (freedom, sockopt.mark = 1)
   │
   ▼
 ядро видит метку 1 → таблица vpn2 → wg1 → портал
```

Ключевая идея: **Xray не несёт трафик до портала, он только принимает решение**.
Соединение он открывает наружу с меткой, а маршрутизирует его ядро — тем же
policy-роутингом, что работает в v1 сегодня (`ip rule from all fwmark 0x1
lookup vpn2`).

Из этого следует главное. К порталу ведёт **один ядерный туннель для всего** —
TCP, UDP, ICMP одинаково. Пинг на зарубежный адрес уходит через портал, как в
v1. Переключение портала — один механизм на все виды трафика, а не два.

Что меняется против v1: решение «напрямую или через портал» принимает Xray по
домену из SNI вместо поиска адреса в ipset. Всё остальное — `wg0`, `wg1`,
dnsmasq, policy-роутинг, MASQUERADE — остаётся как есть.

Foreign-denylist (требование 3 из прошлого списка) становится обычным правилом
в роутинге Xray: перечисленные сети всегда идут в `portal`, независимо от
доменных правил. Это надо записать явно, само оно не появится.

## Что писать

**Экспортёр метрик.** Читает per-peer счётчики `wg0` через netlink и отдаёт в
Prometheus: трафик по клиенту, возраст handshake, текущий endpoint. Через
netlink, а не `wg-quick`, поэтому счётчики не обнуляются при добавлении клиента
— это чинит болячку v1 №2. Плюс статистика Xray по outbound: сколько ушло
напрямую, сколько через портал.

**Монитор и failover.** Проверяет живость портала, при потере переключает `wg1`
на резерв существующим механизмом `groxy bridge use-portal` и пишет в Telegram.
С гистерезисом, чтобы не флапать. Возврат на основной — так же с уведомлением.

**Бот.** Две роли. Админ: добавить, удалить, показать клиентов, QR, кто онлайн,
топ по трафику. Клиент: создать профиль в пределах лимита по количеству,
посмотреть свою статистику, забрать конфиг и QR, кнопка «проверить моё
соединение». Хранит своё сопоставление telegram-аккаунта и профилей.

**Доработки CLI v1:** валидация фида до применения, `dry-run`, автобэкап
состояния с проверкой восстановления.

## Что ставить готовым

Prometheus, Grafana, Alertmanager. Alertmanager шлёт в Telegram — это закрывает
требования 4 и 5 одним каналом.

Алерты из накопленного опыта: протух handshake с порталом; dnsmasq не слушает
на `wg0`; список доменов пуст после обновления; узел недоступен; CPU, память
или диск за порогом; **conntrack у портала подходит к потолку**; клиент не
подключался N дней; handshake рвётся чаще нормы.

Метрикам нужна машина. Ставить их на бридж — плохая идея: он в России, и его
падение унесёт с собой мониторинг ровно тогда, когда он нужен. В роадмапе под
это заложена отдельная VPS, и это решение остаётся в силе.

## Порядок работ

**Ноль, на этой неделе.** Три вещи на проде, каждая по вечеру, все независимые:

- починить резолв DNS на стороне выхода — это причина медленного Steam и самая
  заметная для пользователей правка (`DIAG-SLOW-STEAM.md`);
- поднять `nf_conntrack_max` на портале с 8192 до вменяемого;
- занести MSS-клэмп в репозиторий — сейчас он живёт только в рантайме прода и
  потеряется при переустановке бриджа.

**Первое: наблюдаемость.** Prometheus, экспортёр по пирам, Grafana,
Alertmanager в Telegram. Собственный принцип роадмапа — «раньше админки, без
данных все решения угадывание» — остаётся верным. Заодно после этого станет
видно, действительно ли nether и sweden справляются с нагрузкой.

**Второе: автофейловер.** Ложится поверх health-чеков из первого этапа.

**Третье: Xray как классификатор.** Сначала на тестовом бридже, где уже всё
поднято, потом на проде. Здесь же foreign-denylist и перенос carve-out с ipset
на доменные правила.

**Четвёртое: бот.** Сначала админская часть — она закрывает требование 3 и
убирает SSH из ежедневной работы. Потом клиентское самообслуживание.

**Фоном:** валидация фида, dry-run, автобэкап.

## Риски и оговорки

**Xray всё же терминирует TCP и UDP.** Для проксируемого трафика теряются
сквозной TTL (traceroute по TCP не покажет путь) и ICMP-ошибки вроде
`port unreachable`. Пинг и traceroute в ICMP-режиме работают, потому что идут
мимо Xray. Полностью прозрачным L3 остаётся только то, что не TCP и не UDP.

**Проверка портов через туннель станет врать.** Обнаружено на стенде: TCP-коннект
через прокси-путь всегда рапортует об успехе, даже к нероутируемому адресу.
Диагностировать надо по логам Xray, а не по `nc -z`.

**Сниффинг SNI не вечен.** Разворачивается ECH, при котором настоящее имя
зашифровано. Когда это станет массовым, доменные правила начнут ошибаться, и
подстраховкой останется решение по IP из DNS. Держать оба механизма — не
избыточность, а страховка.

**Мы пишем три компонента вместо нуля.** Экспортёр, монитор и бот. Это меньше,
чем Фаза 0 исходного роадмапа, где планировались свой контроллер, БД и gRPC, но
больше, чем «поставить готовую панель». Плата за то, что требование по ICMP
несовместимо с тем, как панель устроена.

**Веб-интерфейса не будет.** Если через полгода окажется, что бота мало, панель
можно вернуть поверх этой же схемы — данные останутся у нас, а не в её БД.
