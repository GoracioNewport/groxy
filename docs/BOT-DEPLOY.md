# Развёртывание бота и наблюдаемости на бридже

Состояние на 07.09.2026. Готов и проверен на живом узле конвейер снимков;
интерактивная часть бота ещё пишется.

Всё живёт в репозитории `groxy` и выкатывается тем же `git pull` в
`/opt/groxy`, что и CLI. Отдельного репозитория, venv и пакетов из pip нет —
только стандартная библиотека Python.

## Что и где

| Что | Где |
|---|---|
| Модули | `/opt/groxy/bot/groxy_bot/` |
| Снапшоттер | `/opt/groxy/bot/bin/groxy-snapshot` |
| Юниты | `/opt/groxy/bot/systemd/` |
| Токен и список допущенных | `/etc/groxy/bot/` |
| База снимков | `/var/lib/groxy-bot/history.db` |

## Предпосылки

**Python 3.11 и новее.** На боевом бридже 3.11.2, `sqlite3` доступен модулем.
Отдельной утилиты `sqlite3` не нужно.

**`sudo` установлен.** Бот и снимок работают под пользователем `groxy-bot`, а
CLI требует root: файлы пиров лежат с правами 600, а `wg show` без root ничего
не показывает. На боевом бридже `sudo` есть. На тестовом `moscow-25000-01`
его нет — там снимок можно гонять только от root, и это не оплошность
установки, а состояние узла.

Обёртка сама решает, звать ли `sudo`: под root вызывает CLI напрямую. Поэтому
ручной запуск от root работает и на узле без `sudo`.

## Установка

### 1. Пользователь и каталоги

```
useradd --system --no-create-home --shell /usr/sbin/nologin groxy-bot
mkdir -p /var/lib/groxy-bot
chown groxy-bot:groxy-bot /var/lib/groxy-bot
```

### 2. Правило в sudoers

```
install -m 440 /opt/groxy/bot/systemd/groxy-bot.sudoers /etc/sudoers.d/groxy-bot
visudo -c -f /etc/sudoers.d/groxy-bot
```

Проверять обязательно: битый файл в `sudoers.d` ломает `sudo` целиком, включая
собственный вход администратора.

Правило перечисляет подкоманды поимённо, а не `bridge *`. Под звёздочку попали
бы `whitelist set-source` и `use-portal` — смена источника доменов и
переключение портала; боту первой итерации ни то, ни другое не нужно.

### 3. Токен и список допущенных

Токен кладёт владелец сам, значение в диалог не передаётся:

```
install -d -m 750 -o root -g groxy-bot /etc/groxy/bot
# дальше руками, интерактивно, чтобы значение не осело в истории шелла
```

Файл `token` должен быть доступен боту на чтение:

```
chown root:groxy-bot /etc/groxy/bot/token
chmod 640 /etc/groxy/bot/token
```

Список допущенных — `/etc/groxy/bot/allowed-chat-ids`, по одному числу на
строку, `#` начинает комментарий. Пустой список считается ошибкой, а не
«пускать всех»: бот выдаёт и отзывает доступ к VPN, и файл, опустевший из-за
неудачной правки, не должен молча открыть его кому угодно.

### 4. Снимки

```
install -m 644 /opt/groxy/bot/systemd/groxy-snapshot.service /etc/systemd/system/
install -m 644 /opt/groxy/bot/systemd/groxy-snapshot.timer   /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now groxy-snapshot.timer
```

Проверка, что снимок пошёл:

```
systemctl start groxy-snapshot.service
journalctl -u groxy-snapshot -n 20 --no-pager
```

Снапшоттеру токен не нужен — он читает только `load_paths()`. Поэтому снимки
можно включать раньше, чем заведён бот, и программа, не держащая секрета, не
может уронить его в журнал.

### 5. Бот

```
install -m 644 /opt/groxy/bot/systemd/groxy-bot.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now groxy-bot.service
journalctl -u groxy-bot -n 10 --no-pager
```

В журнале при старте должны быть три строки: имя бота, замаскированный токен и
список допущенных `chat_id`. Дальше журнал молчит — длинное опрашивание ничего
не пишет, пока всё в порядке, и это признак нормы, а не тишины после падения.

Юнит не перезапускает бота при коде возврата 3: так он сообщает, что Telegram
не принял токен. Через десять секунд токен годным не станет, а журнал забился
бы одинаковыми строками.

## На порталах: reporter и watchdog

Оба файла самодостаточны и ничего не импортируют — на порталах живёт роль
`portal`, весь groxy там на bash, и пакета `groxy_bot` нет.

### Reporter

Отдаёт память, нагрузку, диск, conntrack и счётчики интерфейсов, плюс
принимает пинги от бота. Слушает **только** на адресе портала внутри
служебного туннеля, поэтому ни токена, ни подписи не имеет: попасть на этот
адрес может лишь тот, у кого уже есть ключ от туннеля.

```
useradd --system --no-create-home --shell /usr/sbin/nologin groxy-reporter
mkdir -p /opt/groxy/bot/bin
# скопировать bot/bin/groxy-reporter и bot/systemd/groxy-reporter.service
systemctl daemon-reload
systemctl enable --now groxy-reporter
```

Проверка с бриджа — обязательно с привязкой к устройству:

```
ssh moscow-1000-01 'curl -s --interface wg1 http://10.77.77.1:9101/metrics'
```

Без `--interface` запрос не уйдёт. Адрес `wg1` на бридже — это `/32`,
маршрута на подсеть туннеля нет, и пакет к 10.77.77.1 отправляется в основную
таблицу через WAN. Бот ходит туда так же, привязкой к устройству; чинить это
маршрутом в шаблоне `wg1` значило бы перезапускать интерфейс ради чтения
метрик.

### Watchdog

Раз в пять минут смотрит на возраст отметки последнего пинга. Молчание дольше
пятнадцати минут — одно сообщение в Telegram **напрямую**: фильтр стоит у
провайдера бриджа, портал Telegram видит.

```
useradd --system --no-create-home --shell /usr/sbin/nologin groxy-watchdog
install -d -m 750 -o root -g groxy-watchdog /etc/groxy/bot
# allowed-chat-ids — тот же файл, что на бридже, права root:groxy-watchdog 640
# скопировать bot/bin/groxy-watchdog и оба юнита
systemctl daemon-reload
systemctl enable --now groxy-watchdog.timer
```

**Токен нужен и здесь.** Без него watchdog пишет в журнал «не настроен» и
выходит с нулём — юнит можно включать заранее, он заработает сам, как только
файл появится. Кладёт токен владелец, тем же способом, что на бридже:

```
# на портале, интерактивно
chown root:groxy-watchdog /etc/groxy/bot/token
chmod 640 /etc/groxy/bot/token
```

### Грабли, которые здесь попались

**`DynamicUser=yes` в юните reporter'а пришлось убрать.** Соблазн был: демону
нужны только `/proc` и сокет. Но systemd кладёт `StateDirectory` такого юнита
в `/var/lib/private`, а он `0700 root:root` — и watchdog под своим
пользователем не смог бы прочитать отметку пинга. Не увидев ни одной отметки,
он после отсрочки закричал бы о смерти бота и кричал бы дальше при совершенно
живом боте.

**`id groxy-reporter` врёт, пока сервис работает под `DynamicUser`.** systemd
публикует временного пользователя через NSS, поэтому условное создание
(`id ... || useradd ...`) молча не срабатывает, а `useradd` отвечает «уже
существует». Сервис надо сначала остановить.

**Песочница юнита наследуется через `sudo`.** `sudo` меняет пользователя, но
не пространство имён, поэтому CLI, запущенный ботом от root, видит ту же
файловую систему, что и юнит. С `ProtectSystem=strict` и одним
`ReadWritePaths=/var/lib/groxy-bot` работали только `stats` и `list-*`: они
ничего не пишут и не берут блокировку. Всё остальное умирало на
`exec 9>/run/groxy.lock` с кодом 1, до первой записи, — состояние оставалось
целым, а причина в журнал не попадала.

Отсюда `ReadWritePaths=/var/lib/groxy-bot /etc/groxy /etc/wireguard /run` в
`groxy-bot.service`. И отсюда же правило: **проверять изменяющие команды надо
изнутри юнита**, а не через `su`. Ручной запуск идёт мимо песочницы и проходит
всегда. Годится `systemd-run` с теми же свойствами:

```
systemd-run --quiet --wait --collect --uid=groxy-bot \
  --property=ProtectSystem=strict --property=ProtectHome=true \
  --property=PrivateTmp=true --property=NoNewPrivileges=no \
  --property="ReadWritePaths=/var/lib/groxy-bot /etc/groxy /etc/wireguard /run" \
  --pipe /usr/bin/sudo -n /opt/groxy/groxy bridge use-portal <активный>
```

Переключение на уже активный портал — пустая операция, но блокировку берёт,
то есть проверяет ровно то, что ломалось.

**`PrivateTmp=true` в списке обязателен**, хотя проверять он ничего не должен.
Рендер `wg0.conf` собирается через `mktemp` в `/tmp`, а `ProtectSystem=strict`
делает `/tmp` только для чтения; настоящий юнит спасает `PrivateTmp`, который
подкладывает туда свою запись. Проба без него даёт ложный отказ
«cannot create a temporary file for wg0.conf» — и хуже того, `add-client`
успевает создать файл пира до этого места, так что за собой она оставляет
профиль, которого нет ни в конфиге, ни в ядре. Лечится `remove-client`:
отсутствующий клиент для него не ошибка, он всё равно доводит состояние до
целого.

**Резервный портал не имеет права судить о живости бота.** Бот пингует только
активный портал — до резервного он через туннель не достаёт вовсе. Поэтому
тревога возможна лишь там, где watchdog сам видел хотя бы один пинг; без этого
условия резервный портал прислал бы «бот не отвечает» при совершенно живом
боте, опираясь на отметку от какой-нибудь ручной пробы. Ровно это чуть не
случилось на `sweden` 07.09.

Обратная сторона: после переключения портала прежний активный пинги уже видел
и через пятнадцать минут закричит. Это записано отдельным пунктом в Фазу 2.

## Автопереключение портала

Работает с 07.09. Пороги задаются переменными окружения юнита, значения по
умолчанию: портал считается нездоровым, когда handshake старше 180 с; переход
случается, если он держится нездоровым ещё 180 с; повторное переключение — не
раньше чем через 1800 с.

Право переключать выдано боту отдельной строкой в
`/etc/sudoers.d/groxy-bot` — это единственная его команда, задевающая сразу
всех клиентов. Отзывается удалением `GROXY_BOT_FAILOVER` из последней строки.

Обратно бот не возвращается сам. Он сообщает, что прежний портал ожил, и
предлагает кнопку в меню «Порталы»: возврат стоит клиентам такого же обрыва,
что и уход, и время для него выбирает владелец.

Проверить пробу, не трогая ничего:

```
ssh moscow-1000-01 'su -s /bin/sh groxy-bot -c "cd /opt/groxy/bot && python3 -c \"
from groxy_bot.failover import Failover
print(Failover.probe_public(\\\"84.22.149.145\\\"))\""'
```

### Как проверять боевой фейловер

Это работа под объявленное окно: два обрыва зарубежного трафика по 5–15 секунд
у всех. На время проверки пороги снижаются через `systemctl edit groxy-bot`,
иначе первый обрыв растянется на шесть минут ожидания:

```
[Service]
Environment=GROXY_FAILOVER_UNHEALTHY=30
Environment=GROXY_FAILOVER_AFTER=30
Environment=GROXY_FAILOVER_COOLDOWN=60
```

После `systemctl daemon-reload` и `systemctl restart groxy-bot` порядок такой:

1. на `nether` — `systemctl stop wg-quick@wg0` (портал перестаёт отвечать);
2. ждём минуту, в Telegram приходит «переключился на sweden»;
3. проверяем выход: `ssh moscow-1000-01 'curl -s --interface wg1 https://ifconfig.me'`
   должен показать адрес `sweden`;
4. на `nether` — `systemctl start wg-quick@wg0`;
5. приходит «прежний портал снова отвечает», возвращаемся кнопкой в меню
   «Порталы»;
6. снимаем переопределение порогов: `systemctl revert groxy-bot`, затем
   `daemon-reload` и `restart`.

Шаг 6 обязателен. С порогом в тридцать секунд бот начнёт переключаться от
любой сетевой икоты, а каждое переключение — обрыв у всех.

## Состояние на боевом бридже

Развёрнуто и работает с 07.09.2026: снимки раз в минуту, бот
`@groxy_controller_bot` и алерты. Пользователь `groxy-bot`, правило в
`/etc/sudoers.d/groxy-bot`, база в `/var/lib/groxy-bot/history.db`.

Проверено там же, что граница sudo работает: `groxy bridge stats --json` из-под
`groxy-bot` проходит, `groxy bridge use-portal sweden` отвергается — то есть
бот не может переключить портал всем клиентам.

`qrencode` нужен для QR и на бридже уже стоит (его ставит `add-client --qr`).
Если его снести, бот не сломается: конфиг всё равно уйдёт файлом, а в журнале
появится строка про отсутствующий `qrencode`.

Раз в минуту бот пишет в журнал одну строку о том, что увидел:

```
INFO проверка: клиентов 36, портал nether, резолвер ок, метрики портала есть, условий 0
```

Это и есть способ отличить работающего наблюдателя от молчащего.

## Что уже проверено на живом узле

Прогон на `moscow-25000-01` 07.09:

- снимок читает состояние через `groxy bridge stats --json`, собирает нагрузку,
  память и диск и пишет связную строку в `peer_samples` и `node_samples`;
- второй прогон обновляет `peer_totals`, накопление поверх счётчиков ядра
  работает;
- база создаётся с правами 600 — в ней endpoint'ы клиентов, то есть адреса, с
  которых люди подключались;
- `systemd-analyze verify` на юните проходит без замечаний;
- под пользователем без `sudo` снимок отказывается внятной строкой
  «не удалось запустить /usr/bin/sudo», а не стеком на пол-экрана.

Не проверено на живом узле: работа таймера под `groxy-bot` — на тестовом узле
нет `sudo`, а на боевом юнит пока не ставился.

## Порядок первого запуска на боевом бридже

Снимки можно включать сразу: они только читают и пишут в свою базу, клиентов
не задевают вовсе. Ставить их стоит **до** бота, чтобы к моменту первых
вопросов «а что было ночью» история уже набралась.

Бот включается после того, как положен токен и заполнен список допущенных.
