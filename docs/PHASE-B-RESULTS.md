## Главный результат: per-client учёт для обычного WireGuard-клиента

Гипотеза, которую стоило проверить первой: AmneziaWG допускает нейтральные
параметры обфускации (`ValidateObfuscation` разрешает `H1–H4` от нуля и нулевые
джиттеры), а в таком виде AWG протокольно совпадает с обычным WireGuard.

Проверено — работает. AWG-инбаунд с `jc/jmin/jmax = 0`, `s1–s4 = 0`,
`h1–h4 = 1,2,3,4`, без header protection, принял **ядерного WireGuard-клиента**
без единой правки на его стороне:

```
peer: 4Cu7Ve4pTwicYzjY6Pt5UUggdkrDtHkimVEppG5iajk=
  latest handshake: 23 seconds ago
  transfer: 476 B received, 564 B sent
```

И при этом панель считает трафик **по клиенту**. После загрузки 10 МБ через
туннель `GET /panel/api/clients/traffic/stand-awg-1` вернул:

```json
{"email":"stand-awg-1","up":1558,"down":10486678,"lastOnline":1788339437007}
```

`down` совпадает с размером файла байт в байт.

Это снимает главный размен всей схемы. В `STAND-3XUI-RESULTS.md` он записан так:
«нативный WG-клиент = нет per-client учёта/квот в панели», и из него росли
варианты «смириться» либо «увести клиентов на Reality». Ни то, ни другое больше
не нужно: тупой WG-клиент на роутере и полноценный per-client учёт с квотами
совместимы, если инбаунд объявлен как `amneziawg` с нейтральной обфускацией.

Побочно это же даёт путь наращивания: обфускацию на том же инбаунде можно
включить позже для тех клиентов, кто умеет AWG, не трогая остальных.

## Как это устроено внутри

Панель разворачивает AWG-инбаунд в пару «встроенный интерфейс + SOCKS-инбаунд»:

```
amneziawgnet: started embedded interface awg1 for inbound 1
```

В сгенерированном `bin/config.json` появляется:

```
tag = in-51830-udp, protocol = socks, listen = 127.0.0.1:65101
  accounts: [{user: "stand-awg-1", pass: <генерируется панелью>}]
  sniffing: enabled, destOverride = [http, tls, quic, fakedns]
```

То есть gVisor-netstack декапсулирует WG и отдаёт трафик в SOCKS-инбаунд Xray,
где **на каждого клиента заведён отдельный аккаунт** — отсюда и per-client
счётчики (`user>>>email>>>traffic`). Ядерного интерфейса нет вообще: UDP-порт
51830 слушает сам процесс `x-ui`.

Важное следствие: **sniffing на этом инбаунде включён из коробки**, значит
доменный carve-out для AWG-клиентов доступен сразу, без ручной правки конфига.
Это ровно тот механизм, ради которого затевался переход с ipset-схемы v1.

### DNS — решено 02.09

Встроенный путь не поднимает DNS-ответчик на адресе сервера в туннеле: запрос
на `10.99.0.1:53` уходит в netstack и умирает по таймауту. Отдельного DNS-
ответчика там просто нет, и добавить его настройками нельзя.

Решение оказалось другим и работает без единой правки кода: **не трогать адрес
шлюза, а направить клиентов на уже работающий dnsmasq v1-бриджа** по адресу
`10.66.66.1`. Для клиента это тот же адрес, что зашит у него в `.conf` сегодня,
то есть критерий Фазы C выполняется буквально.

Само по себе это не заработало, и мешали **два** разных запрета, а не один:

1. В роутинге Xray правило `geoip:private → blocked` рубит любой приватный
   адрес. Лечится правилом выше него:

   ```json
   {"type": "field", "ip": ["10.66.66.1/32"], "port": "53", "outboundTag": "direct"}
   ```

2. Этого мало. У outbound `direct` (freedom) в собственных `finalRules` стоит
   второй, независимый запрет на приватные адреса, и он глушит запрос уже
   на выходе — в логе это видно дословно:

   ```
   app/dispatcher: taking detour [direct] for [udp:10.66.66.1:53]
   proxy/freedom: blocked target: udp:10.66.66.1:53, blackholing connection for 1m22s
   ```

   Лечится исключением в начале `finalRules` того же outbound:

   ```json
   {"action": "allow", "ip": ["10.66.66.1/32"]}
   ```

Диагностическая деталь, которая сэкономит время в следующий раз: TCP-коннект на
`10.66.66.1:53` проходил, когда UDP-запрос ещё не работал. Это и подсказало, что
дело не в роутинге, а в выходе.

После обоих изменений с клиентским резолвером `10.66.66.1` резолв идёт, HTTPS
через туннель работает, выход с `193.233.246.86`. Правила переживают
перезапуск панели.

Что учесть при переводе прода (Фаза D): адрес `10.66.66.1` сейчас принадлежит
интерфейсу `wg0` v1-бриджа. Когда `wg0` будет погашен, адрес и слушающий на нём
dnsmasq надо сохранить — например, повесив `10.66.66.1` на dummy-интерфейс.
То есть dnsmasq остаётся частью схемы осознанно, а не по недосмотру.

### ICMP — не чинится настройками, нужен код

Пинг наружу из туннеля не проходит, пинг до шлюза проходит. Причина разобрана
по коду и совпадает с разбором upstream в issue #6366 (открыт, помечен как
feature request):

- `netstack.go:62` регистрирует `icmp.NewProtocol4/6` — поэтому эхо на
  собственный адрес интерфейса netstack отвечает сам;
- но обработчик привязан только к двум протоколам: TCP в `forwarder.go:42` и
  UDP в `udp.go:34`. Для ICMP обработчика нет;
- всё, что уходит наружу, уходит через SOCKS5 в Xray (`relay.go`), а в RFC 1928
  нет команды, способной перенести ICMP-эхо. На этом пути ICMP непредставим
  в принципе.

Мы заодно закрыли вопрос, который в том же issue остался нерешённым: не
подделывает ли gVisor в promiscuous-режиме эхо-ответы за произвольные адреса,
из-за чего пинг «проходил» бы фиктивно. Не подделывает — `ping 8.8.8.8` даёт
ровно 100% потерь.

Настройками это не лечится. Варианты — только через код:

1. **Релей ICMP в панели.** Повесить обработчик на `icmp.ProtocolNumber4`,
   отправлять эхо с хоста (панель работает от root, raw-сокет доступен) и
   инжектить ответ обратно в netstack по образцу `WriteUDPReply`. Нужен NAT по
   полю Echo ID, чтобы не путать клиентов. Объём — сопоставим с `udp.go`.
   Минус: ICMP пойдёт мимо Xray, то есть мимо правил роутинга — пинг
   зарубежного адреса уйдёт с IP бриджа, а не через портал.
2. **Ядерный datapath.** Возврат к снятой архитектуре (DKMS + awg-quick +
   TPROXY). Чинит ICMP, client-to-client и скорость разом, но ломает
   per-client учёт: идентичность клиента сейчас берётся из имени SOCKS5-
   аккаунта, а мимо релея её взять неоткуда. В upstream это обсуждается в
   issue #6378, решения нет.

### Скорость — вопрос снят

Первая цифра (1,6 МБ/с) была ошибкой замера: столько же выдавало то зеркало
напрямую с хоста, без всякого туннеля. Мерился канал до зеркала, а не путь.

Правильные замеры, одно зеркало (`mirror.yandex.ru`), один TCP-поток, 20 секунд:

| Что мерим | Скорость |
|---|---|
| С хоста напрямую, без туннеля и Xray | 663 Мбит/с |
| С хоста через SOCKS-релей инбаунда, без туннеля | 1277 Мбит/с |
| Через туннель, клиент в netns на том же хосте (RTT 0,4 мс) | **355 Мбит/с** |
| С nether напрямую, без туннеля (RTT 47 мс) | 126 Мбит/с |
| С nether через туннель (RTT 47 мс) | **119 Мбит/с** |

На реальном WAN-плече туннель стоит около 6% от скорости канала. «Жёсткий
потолок 57 Мбит/с», о котором сообщают в issue #6378, на нашем железе не
воспроизводится: 1 vCPU, тот же встроенный путь, 355 Мбит/с локально.

Осторожность: замеры однопоточные и последовательные, зеркало могло отдавать
из кэша. Но порядок величины отличается от сообщений в треде в шесть раз, и под
наш парк встроенный путь по скорости проходит.
