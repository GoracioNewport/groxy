## Фаза E — Второй портал и failover (схема утверждена)

Требование: **nether всегда основной**, переключение на резерв только при его
недоступности либо вручную из админки. Это не балансировка нагрузки —
`leastPing`/`roundRobin` поверх двух порталов не подходят, они размазывают трафик.

Рабочая конфигурация (проверена на стенде целиком):

```json
"routing": {
  "balancers": [{
    "tag": "portals",
    "selector": ["portal-nether"],      // в отборе ТОЛЬКО основной
    "fallbackTag": "portal-sweden",     // резерв — когда основной не прошёл health-чек
    "strategy": {"type": "leastPing"}
  }],
  "rules": [{ "...": "...", "balancerTag": "portals" }]
},
"burstObservatory": {
  "subjectSelector": ["portal-nether"], // пробим только основной
  "pingConfig": {"destination":"https://www.google.com/generate_204",
                 "interval":"5s","timeout":"3s","sampling":2}
}
```

Механика: `fallbackTag` в ядре срабатывает, когда балансировщик не нашёл живых
кандидатов (`app/router/balancing.go`). Раз в селекторе только nether, то пока он
здоров — выбирается всегда он; умер — отбор пуст и трафик уходит на sweden;
поднялся — возвращается сам.

Подтверждено замерами счётчиков:
- основной жив → резерв **ровно 0/0**;
- убил основной → резерв ушёл с нуля, клиент продолжил работать (потерян 1 запрос
  в момент переключения, переподключать WG не требуется);
- поднял основной → резерв застыл, трафик вернулся на основной автоматически.

**Ручное переключение** — в рантайме, без рестарта Xray и без разрыва клиентов:

```bash
xray api bo -s 127.0.0.1:10085 -b portals portal-sweden   # принудительно на резерв
xray api bo -s 127.0.0.1:10085 -b portals -r              # снять, вернуть автоматику
xray api bi -s 127.0.0.1:10085 portals                    # кто выбран сейчас
```

Требует `"services": ["StatsService","RoutingService"]` в `api`. Проверено:
override увёл трафик на резерв при живом основном, `-r` вернул на основной.

## Роутинг: как настраивается (вопрос 5)

Панель везёт `geosite_RU.dat` — там готовые категории под РФ:

```
category-ru                 российские сервисы (общая)
ru-available-only-inside    работает только с российского IP  ← главный carve-out
ru-blocked / ru-blocked-all заблокировано в РФ                ← гнать через портал
refilter                    список reFilter
category-gov-ru, -bank-ru, -media-ru, -ecommerce-ru, -retail-ru,
category-medicine-ru, -travel-ru, -entertainment-ru, -ai-ru, -betting-ru
mailru, nic-ru, mts-ru, regru
```

Базовая конфигурация правил (порядок важен, сверху вниз):

```
1. geosite:ru-available-only-inside  → direct   (иначе просто не работает)
2. geosite:category-ru               → direct   (RU-сервисы с российского IP)
3. geoip:ru                          → direct   (страховка по IP)
4. YouTube-семья                     → portal-RU-гео (см. ниже)
5. geosite:ru-blocked                → portal
6. всё остальное                     → portal
```

Свои списки — тремя способами, все проверены/штатны:
- инлайн-массив `domain` в правиле (19 700 доменов = 14 мс, 35 МБ — opencck-фид
  переносится как есть);
- свой скомпилированный `.dat` и ссылка `ext:my.dat:category`;
- поверх этого — управление geodata есть в UI панели (`GeodataSection`).

**Отдельно про YouTube без рекламы.** Реклама определяется страной, которую Google
присваивает IP. Замеры: `nether` и `moscow-25000-01` → `GL=RU` (рекламы нет),
`sweden-300-01` → `GL=GB` (реклама есть). Значит семью доменов
`youtube.com`, `googlevideo.com`, `ytimg.com`, `youtubei.googleapis.com` надо
направлять на узел с RU-гео. Проверка любого IP:
`curl -s -H 'Cookie: SOCS=CAI' https://www.youtube.com/ | grep -oE '"GL":"[A-Z]{2}"'`
(скрипт: `yt-adcheck.sh`). Оговорка: у залогиненного пользователя YouTube может
брать страну аккаунта, а не IP.

## Метрики: что будет видно (вопрос 4)

| Метрика | Источник | Статус |
|---|---|---|
| Сквозной throughput по системе и по узлу | Xray Stats per-inbound/per-outbound | есть, проверено |
| Трафик «через портал» vs «напрямую» | счётчики по outbound-тегам | есть, проверено |
| CPU / RAM / сеть / uptime по каждой ноде | таблица `nodes` (`cpu_pct`, `mem_pct`, `net_up/down`) | есть в схеме |
| CPU/RAM хоста панели + алерты | джобы `check_cpu_usage`, `check_memory_usage` | есть |
| Per-client трафик (VLESS/Trojan/SS) | `user>>>email>>>traffic` → `client_traffics` | есть |
| Per-client трафик по узлам | `node_client_traffics`, `client_global_traffics` | есть в схеме |
| **Per-client трафик для нативных WG-пиров** | — | **НЕТ** (ограничение ядра Xray) |
| Per-client трафик для AWG | kernel `awg show` в PR #6105 | обещано, проверить в фазе B |

Счётчики висят на интерфейсах, а не на пирах, поэтому **не обнуляются** при
добавлении/удалении клиента — это чинит проблему v1 №5.

## Риски

1. **PR #6105 могут не влить в upstream** — тогда форк живёт с ним вечно и каждый
   rebase дороже. Это осознанная цена варианта 3.
2. **Автор PR не продумывал миграцию существующих AWG-пользователей** — у нас их
   нет, поэтому не блокирует.
3. **Нативные WG-клиенты остаются без per-client учёта.** Варианты: смириться
   (как в v1), увести часть клиентов на AWG/Reality, либо (в форке) читать
   счётчики по пирам самим.
4. **Окно простоя при переводе прода** — порт занимает либо wg0, либо Xray.
5. Панель слушает наружу: держать нестандартный порт, случайный base-path,
   fail2ban (ставится сам), в идеале — бинд на localhost + доступ через туннель.
