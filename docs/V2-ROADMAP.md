# groxy v2 — архитектура и роадмап

Статус: черновик, утверждён на уровне ключевых развилок (2026-08-09).

v1 (bash + SSH вручную) остаётся в проде до завершения Фазы 1. Ничего из
описанного ниже не ломает работающую установку: миграция идёт с сохранением
клиентских конфигов.

## 1. Зачем v2

v1 решил задачу «поднять каскадный VPN». Эксплуатация вскрыла другой класс
проблем — управляемость и наблюдаемость:

- **Нет истории.** Причину инцидента с клиентом получилось установить только
  случайно — сравнив endpoint до и после. `wg` хранит лишь последний handshake.
- **Счётчики обнуляются** при каждом `add-client`/`remove-client` (там
  перезапускается `wg-quick@wg0`), поэтому статистики по трафику фактически нет.
- **Нет алертов.** Race с привязкой dnsmasq к wg0 и опустевший `vpn_domains`
  ловились руками, постфактум, по жалобам.
- **Мусор в carve-out.** `vpn_domains` — hash:ip без TTL; ложные записи
  (IP-блоки, разделяемые с зарубежными сервисами) дважды ломали доступ к
  ChatGPT. Ежедневный flush уменьшил накопление, но не устранил причину.
- **Ручное управление.** Каждый выпуск профиля — SSH и команда. Не масштабируется
  на 36+ клиентов, не делегируется.
- **Состояние живёт на нодах.** Нет единого источника правды, нечем
  реконсилировать расхождения, невозможен автоматический failover.

## 2. Ключевые решения

| Развилка | Решение | Обоснование |
|---|---|---|
| Язык | **Go** (агент и контроллер) | `wgctrl-go` управляет WireGuard через netlink — без парсинга конфигов и рестарта интерфейса (попутно чинит обнуление счётчиков). Статический бинарь без зависимостей на VPS. Единый стек проще поддерживать. |
| Транспорт | **gRPC + mTLS**, агент на каждой ноде | Нужны потоковые метрики, reconcile-loop и быстрый failover. Через SSH это только поллинг и костыли. |
| Источник правды | **БД контроллера** | Ноды становятся исполнителями. Расхождение лечится реконсиляцией, а не ручной правкой файлов. |
| Размещение контроллера | Отдельная VPS вне РФ | Не падает вместе с бриджем; админка и бот должны быть доступны всегда. |
| Приватные ключи клиентов | **Не хранить** (только pubkey) | Генерируем, отдаём один раз, забываем. Повторный показ QR = перевыпуск. Безопаснее и проще, чем шифрованное хранилище. |

## 3. Архитектура

```
                    ┌─────────────────────────────┐
                    │      groxy-controller       │   control plane
                    │   API · БД · планировщик    │   (отдельная VPS)
                    └──────────┬──────────────────┘
                               │ gRPC / mTLS
            ┌──────────────────┼──────────────────┐
            ▼                  ▼                  ▼
      groxy-agent        groxy-agent        groxy-agent
      (bridge RU)        (portal NL)        (bridge backup)
      wgctrl · nft       wgctrl             …
      dnsmasq · ipset
            │
            └─→ metrics ─→ Prometheus ─→ Grafana + Alertmanager

  Потребители API:   admin-ui (web)   │   telegram-bot   │   groxyctl (CLI)
```

**Агент** — тонкий. Умеет: сообщить текущее состояние, привести ноду к
желаемому (reconcile), отдать метрики, выполнить диагностику. Не принимает
решений.

**Контроллер** — вся бизнес-логика: клиенты, профили, назначение на ноды,
генерация конфигов, health-чеки, failover, аудит.

### Структура репозитория

Монорепо; v1 остаётся в корне нетронутым до миграции.

```
groxy/
├── cmd/
│   ├── groxy-agent/          # демон на нодах
│   ├── groxy-controller/     # control plane
│   └── groxyctl/             # CLI поверх API (замена bash-командам)
├── internal/
│   ├── agent/
│   │   ├── wg/               # wgctrl: пиры, интерфейсы
│   │   ├── firewall/         # nft/iptables: mangle, mss-clamp, nat
│   │   ├── dns/              # dnsmasq + ipset
│   │   └── diag/             # самодиагностика ноды
│   ├── controller/
│   │   ├── api/              # HTTP/gRPC для UI и бота
│   │   ├── reconcile/        # desired → actual
│   │   ├── failover/
│   │   └── profiles/         # генерация wg/awg конфигов, QR
│   ├── store/                # БД (Postgres), миграции
│   └── proto/                # gRPC-контракты
├── deploy/                   # systemd, provisioning новой ноды
├── docs/
├── groxy, lib/               # v1 (legacy, до миграции)
```

## 4. Схема данных (черновик)

```sql
nodes            id, name, role(bridge|portal), public_ip, agent_addr,
                 status, os, agent_version, created_at, last_seen_at

tunnels          id, bridge_node_id, portal_node_id, subnet,
                 bridge_ip, portal_ip, bridge_pubkey, portal_pubkey,
                 priority, is_active            -- priority для failover

users            id, name, telegram_id, role(admin|user),
                 profile_quota, is_active, created_at

profiles         id, user_id, name, protocol(wireguard|amneziawg),
                 node_id, address, pubkey,
                 expires_at, traffic_quota_bytes, routing_policy_id,
                 created_at, revoked_at

handshakes       profile_id, ts, endpoint_ip, endpoint_port,
                 rx_bytes, tx_bytes          -- снимок раз в минуту

node_metrics     node_id, ts, cpu, mem, net_rx, net_tx,
                 peers_total, peers_online, tunnel_handshake_age

routing_policies id, name, mode(full|split), whitelist_sources, denylist_id

audit_log        id, actor_id, action, target_type, target_id, payload, ts
```

Заметки:
- `handshakes` — по сути time-series. На нашем объёме (≈50 профилей × 1440
  снимков/сутки) обычной таблицы с ретеншеном и партиционированием по дню
  достаточно; отдельная TSDB избыточна.
- `priority` в `tunnels` — основа автоматического failover: бридж переключается
  на следующий по приоритету портал.

## 5. gRPC-контракт агента (набросок)

```proto
service Agent {
  rpc GetState   (Empty)         returns (NodeState);        // что есть сейчас
  rpc Apply      (DesiredState)  returns (ApplyResult);      // привести к желаемому
  rpc StreamMetrics (Empty)      returns (stream Metrics);   // непрерывно
  rpc Health     (Empty)         returns (HealthStatus);
  rpc Diagnose   (DiagRequest)   returns (DiagResult);       // ping/dns/ipset/mtu
}
```

`Apply` идемпотентен и декларативен: контроллер шлёт желаемое состояние целиком,
агент вычисляет дельту. Никаких императивных «добавь пира».

## 6. Роадмап

### Фаза 0 — Фундамент ← **начинаем отсюда**

- [ ] Схема БД + миграции
- [ ] gRPC-контракты (proto)
- [ ] `groxy-agent` MVP: `GetState` / `Apply` для WireGuard-пиров через wgctrl
- [ ] Управление firewall/dnsmasq/ipset в агенте (перенос логики из bash)
- [ ] `groxy-controller` MVP: БД, reconcile-loop, минимальный API
- [ ] `groxyctl`: паритет с текущими bash-командами
- [ ] **Импорт существующих клиентов без смены их конфигов** (ключи, IP, порт
      сохраняются — как при переезде на repo-based v1)
- [ ] mTLS-инфраструктура (CA, выдача сертификатов нодам)

Критерий готовности: на тестовой паре нод весь текущий функционал v1 работает
через контроллер, клиентские конфиги не менялись.

### Фаза 1 — Парк машин

- [ ] Ввод нового основного портала, вывод/резервирование `nether-2000-01`
- [ ] Перевод `sweden-300-01` из тестового контура в резервный портал
- [ ] Provisioning новой ноды одной командой
- [ ] Единое обновление агентов

Целевой парк — см. раздел 9.

### Фаза 2 — Наблюдаемость

Раньше админки: без данных все последующие решения — угадывание.

- [ ] История подключений (снимок раз в минуту → БД)
- [ ] **Throughput: сквозной и по узлам.** В админке должно быть видно, сколько
      трафика проходит через систему в целом и через каждый узел в отдельности —
      мгновенная скорость и накопленные объёмы за период. Считаем на агенте по
      счётчикам интерфейсов (`wg0`, `wg1`, egress) — они не зависят от рестартов
      пиров, в отличие от per-peer счётчиков WireGuard.
- [ ] Метрики: per-client (rx/tx, возраст handshake, endpoint),
      per-node (CPU/RAM/net, число пиров), per-tunnel (latency, потери, throughput)
- [ ] Экспорт в Prometheus, дашборды в Grafana
- [ ] Логи в Loki — диагностика клиентских проблем без SSH

### Фаза 3 — Алерты и failover

- [ ] Health-чеки каждого звена: клиент→bridge, bridge→portal, portal→интернет,
      DNS, ipset
- [ ] Проверки из накопленного опыта: dnsmasq не слушает на wg0; `vpn_domains`
      пуст; handshake с порталом протух
- [ ] Alertmanager → Telegram
- [ ] Автопереключение на резервный портал (с гистерезисом против флапа)

### Фаза 4 — Админская панель

- [ ] Дашборд: ноды, туннели, клиенты онлайн, трафик
- [ ] CRUD клиентов, выпуск/отзыв профилей, QR
- [ ] Настройка whitelist/GeoIP/denylist из UI
- [ ] Аудит-лог

### Фаза 5 — Клиентский self-service

- [ ] Telegram-бот: админ выдаёт `telegram_id` квоту на N профилей
- [ ] Пользователь сам создаёт / удаляет / перевыпускает профиль, получает QR
- [ ] Кнопка «проверить моё соединение» → handshake, трафик, подсказка
      («туннель залип — переключи»). Закрывает типовое обращение без админа.
- [ ] Уведомления: профиль истекает, квота исчерпана

### Фаза 6 — Мульти-протокол

- [ ] Абстракция «профиль = протокол + параметры»
- [ ] AmneziaWG вторым интерфейсом на бридже (рабочие параметры обфускации уже
      есть в текущем клиентском сетапе)
- [ ] Выбор протокола при выпуске профиля

## 7. Дополнительные фичи

**Операционные — высокая отдача, дёшево:**
- **Foreign-denylist** — сети (OpenAI, зарубежный Cloudflare), которые *всегда*
  идут через портал, независимо от содержимого `vpn_domains`. Закрывает баг,
  который ловили дважды.
- Валидация whitelist-фида до применения (не пуст, домены резолвятся, нет
  пересечений с denylist)
- Автобэкап состояния с проверкой восстановления
- `dry-run` применения конфигурации

**Клиентские:**
- Срок действия профиля (гостевой доступ)
- Квоты трафика
- Группы и политики роутинга (полный туннель / только заблокированное)
- Выбор гео-выхода при нескольких порталах
- Плановая ротация ключей

**Диагностика:**
- Топ клиентов по трафику за период
- Детектор проблемных профилей («не подключался N дней», «handshake рвётся
  чаще нормы»)
- Детектор DNS-утечек

## 8. Открытые вопросы

- Схема БД — черновик, уточняется при реализации Фазы 0.
- Веб-фреймворк админки не выбран (server-side + htmx против SPA).
- Нужен ли отдельный агент на портале или достаточно урезанного — портал проще
  бриджа (нет dnsmasq/ipset/mangle).
- Судьба `nether-2000-01` после ввода нового портала: третий резерв или вывод.
- Отдельная тема, вне groxy: клиентский mihomo использует userspace-WireGuard,
  и это даёт залипания и просадки throughput. Кандидат на переход к
  kernel-WireGuard с маршрутизацией поверх.

## 9. Парк машин

Замеры существующих узлов (2026-08-10):

| Узел | Роль сейчас | vCPU | RAM | Диск (своб.) | Провайдер |
|---|---|---|---|---|---|
| `moscow-1000-01` | prod bridge, 36 клиентов | 2 | 3.9 ГБ | 29 ГБ (26) | Cloud.ru (SberCloud), Москва |
| `nether-2000-01` | prod portal | 1 | 0.9 ГБ | 9.9 ГБ (**4.0**) | Амстердам |
| `sweden-300-01` | test portal | 1 | 3.9 ГБ | 9.8 ГБ (7.6) | Aeza |
| `moscow-25000-01` | test bridge | 1 | 2.0 ГБ | 30 ГБ (27) | Москва |
| `moscow-1000-white` | test bridge за 1:1 NAT | — | — | — | Yandex.Cloud |

Нагрузка на CPU у всех околонулевая (LA ≈ 0) — WireGuard дёшев, узкое место не
здесь. Проблема в другом: у прод-портала **960 МБ RAM и 4 ГБ свободного диска**
при том, что через него идёт весь зарубежный трафик. Это кандидат на замену.

### Целевой парк

| Узел | Роль | Действие |
|---|---|---|
| `moscow-1000-01` | Bridge RU (основной) | оставить |
| новый Aeza #1 | **Portal (основной)** | купить: 2 vCPU, 4 ГБ, 40+ ГБ, безлимит |
| `sweden-300-01` | Portal (резервный) | перевести из теста в прод |
| новый Aeza #2 | **Controller + мониторинг** | купить: 2 vCPU, 4 ГБ, 60+ ГБ |
| `nether-2000-01` | третий резерв либо вывод | решить после миграции |
| `moscow-25000-01` | тестовый bridge, временно роль резервного входа | оставить |

Резервный вход (второй bridge у другого провайдера) отложен: клиентский
`Endpoint` зашит в конфиги, поэтому переключение входа в любом случае требует
второго профиля на устройстве. Пока эту роль играет `moscow-25000-01`.

### Почему контроллер — отдельная машина

Рассматривалось размещение на портале ради экономии. Отклонено:

1. **Не влезает.** У существующих порталов диск 10 ГБ; Postgres + Prometheus +
   Grafana + Loki требуют места, и метрики растут.
2. **Радиус отказа.** Контроллер обязан пережить падение любого узла данных —
   иначе некому выполнить failover. На портале падение узла означает потерю
   доступа, админки и механизма переключения одновременно.
3. **Обновления.** Рестарт машины ради обновления контроллера рвал бы туннели
   клиентов.

### Требования при заказе

- Портал: **безлимитный трафик** — через него идёт весь зарубежный обмен.
- Контроллер: **диск от 60 ГБ** — метрики и история подключений.
- Локации портала и контроллера — разные; резервный портал обязательно в другой
  локации, иначе ляжет вместе с основным.
- Статический публичный IP у всех узлов: адрес бриджа зашит в клиентских
  конфигах, адреса порталов — в конфигурации бриджей.
- Открыть входящий UDP на порт WireGuard в фаерволе/Security Groups облака.
  Типичная причина «клиент не подключается» — закрытый порт, снаружи выглядит
  как полная тишина.
