# Уборка Фазы 0: что сделано и что осталось на руки

Снято 06.09.2026. Разбор реестров пиров на обоих порталах и инвентаризация
стендов на `moscow-25000-01` и `nether-2000-01`.

Часть работы упёрлась в ограничения среды: классификатор auto-режима пропускает
`ip netns del` и `ip link del`, но отклоняет `systemctl`, `rm -rf` и
`groxy portal remove-bridge` на удалённых узлах. Команды ниже готовы к
выполнению, обходить запрет никто не стал.

## Кто есть кто: сопоставление по ключам

Публичный ключ — единственный надёжный идентификатор, имена и адреса
назначаются на каждом портале отдельно.

| Ключ | Машина | На `nether` | На `sweden` |
|---|---|---|---|
| `qPHb510a…Oazw=` | `moscow-1000-01`, боевой бридж | `moscow` / 10.77.77.2 | `moscow-main` / 10.77.77.4 |
| `Fdu/bhlv…GN1E=` | `moscow-25000-01`, тестовый узел | — | `moscow-test` / .2 **и** `moscow-test-v2` / .3 |
| `+QhSbMhJ…49jA=` | неизвестна, endpoint 84.201.147.122 | `moscow-1000-white` / 10.77.77.3 | — |

Сверено с `/etc/groxy/bridge/public.key` на самих узлах и с их
`portals/*/portal.env`.

## Поправка: в ядре побеждает последняя запись, не первая

`PLAN-V2.md` утверждал, что из пары `moscow-test` и `moscow-test-v2` активна
первая. Живое состояние `sweden` говорит обратное:

```
peer: Fdu/bhlvc+RRzf7QW6OI5Mx/+upeuiHjQFRWEHHGN1E=
  endpoint: 193.233.246.86:36178
  allowed ips: 10.77.77.3/32
  latest handshake: 1 minute ago
```

10.77.77.3 — это `moscow-test-v2`, и именно он совпадает с тем, что
`moscow-25000-01` считает своим адресом (`TUNNEL_BRIDGE_IP=10.77.77.3`). Обе
записи попадают в рендер `wg0.conf`, `wg setconf` применяет их по порядку, и
вторая перезаписывает первую.

**Отсюда порядок работ.** Победитель определяется алфавитным порядком имён
файлов в `portal/bridges/`. Пока дубль не снят, переименовывать `moscow-test-v2`
нельзя: любое имя, сортирующееся раньше `moscow-test`, отдаст победу мёртвой
записи с адресом 10.77.77.2, и туннель тестового узла отвалится. Сначала снять
дубль, потом переименовывать.

## Осталось: команды на руки

### 1. Снять дубль на резервном портале

Конфиг и живое состояние уже забэкаплены в `/root/wg0.conf.bak-2026-09-06` и
`/root/wg0.showconf.bak-2026-09-06`.

```
ssh sweden-300-01 '/opt/groxy/groxy portal remove-bridge moscow-test'
```

Команда перерендерит `wg0.conf` и перезапустит `wg-quick@wg0`. Прод идёт через
`nether`, поэтому задевает только туннель `moscow-25000-01` — секунды. После
выполнения набор пиров должен стать: `qPHb510a…` (10.77.77.4) и `Fdu/bhlv…`
(10.77.77.3), тот же, что и сейчас в ядре.

### 2. Погасить стенд на тестовом узле

```
ssh moscow-25000-01 'systemctl disable --now x-ui'
ssh moscow-25000-01 'rm -rf /usr/local/x-ui /etc/systemd/system/x-ui.service'
ssh moscow-25000-01 'systemctl daemon-reload'
```

Вместе с `x-ui` уходит его база, а с ней пароль SOCKS-инбаунда со стенда —
перевыпускать нечего, инбаунд удаляется целиком.

Остаётся отдельный процесс `xray` с конфигом бенчмарка, он не под systemd:

```
ssh moscow-25000-01 'pkill -f /root/bench/vless-local.json'
```

Временные скрипты и бинари стенда, ~200 МБ:

```
ssh moscow-25000-01 'rm -rf /root/bench /root/awglocal /root/wg9 /root/xray-stand /root/x-ui-v370'
ssh moscow-25000-01 'rm -f /root/x-ui.fork /root/x-ui.fork-build-20260812.bak /root/x-ui.vanilla.bak /root/x-ui.db.bak-2026-09-02'
ssh moscow-25000-01 'rm -f /root/add-inbounds.py /root/add-local-client.py /root/add-loc-client.py /root/awg-create.py /root/bench.py /root/cpusample.py /root/kernel-wg.py /root/local-clients.py /root/proto-bench.py /root/speedtest-netns.py /root/speedtest-netns.sh /root/xray-tpl.py /root/tester.conf'
```

Проверка после: наружу должен остаться только 22-й порт.

```
ssh moscow-25000-01 'ss -lntp | grep -v 127.0.0.1'
```

### 3. Погасить стенд на боевом портале

На `nether` с 12 августа работают два `xray` из `/root/xray-stand`, слушающие
`0.0.0.0:8443` и `0.0.0.0:8445` — это остатки замеров Reality, снаружи доступны

```
ssh nether-2000-01 'pkill -f /root/bench/vless-client.json'
ssh nether-2000-01 'rm -rf /root/bench /root/awgtest /root/xray-stand'
```

`/root/xray-stand` — 109 МБ на узле, где свободно 3,7 ГБ.

Проверка: наружу остаются 22 и порт портала 61285/udp.


## Осталось: два решения за владельцем

### Мёртвый пир `moscow-1000-white` на боевом портале

```
peer: +QhSbMhJJ6kTLQTEZu8KPnu4bW48RPImpMvz5dM49jA=
  endpoint: 84.201.147.122:39885
  allowed ips: 10.77.77.3/32
  latest handshake: 36 days, 6 hours ago
  transfer: 966.52 MiB received, 7.05 GiB sent
```

Машины с таким адресом нет ни в целевом парке, ни в `~/.ssh/config`. Ключ
рабочий: владелец приватной половины в любой момент поднимет туннель и получит
выход через боевой портал. Трафик за всё время — 7 ГБ, то есть узел работал.

Либо это отставленный бридж и запись пора снять, либо машина нужна и её надо
занести в парк. Снимается так:

```
ssh nether-2000-01 '/opt/groxy/groxy portal remove-bridge moscow-1000-white'
```

Внимание: команда перезапускает `wg-quick@wg0` на **боевом** портале — все 36
клиентов теряют зарубежный трафик на несколько секунд. Это работа под окно, а
не попутная.

### Схема имён

Сегодня одна и та же машина зовётся `moscow` на одном портале и `moscow-main`
на другом. Разумная схема — имя пира совпадает с именем узла в парке:

| Ключ | Сейчас | Предлагается |
|---|---|---|
| `qPHb510a…` | `moscow` / `moscow-main` | `moscow-1000-01` на обоих |
| `Fdu/bhlv…` | `moscow-test-v2` | `moscow-25000-01` |
| `+QhSbMhJ…` | `moscow-1000-white` | решается вместе с судьбой пира |

Переименование — это `mv` файла в `portal/bridges/`, ключ и PSK не меняются,
рендер отличается одной строкой комментария. Но применять его надо после снятия
дубля и, на `nether`, в то же окно, что и остальные работы с `wg-quick@wg0`.

## Что ещё всплыло по дороге

**`portal remove-bridge` перезапускает интерфейс.** На бридже `wg syncconf`
уже заменил перезапуск, на портале — нет. Для резервного портала это неважно,
для боевого означает, что любая правка реестра пиров стоит окна. Кандидат в
Фазу 5.

**Дубликат публичного ключа при регистрации никто не проверяет.** Именно так и
появилась пара `moscow-test` / `moscow-test-v2`: одна машина зарегистрирована
дважды, оба раза успешно. Проверка уже стоит в Фазе 5, этот случай — её живое
обоснование.

**Версии кода на порталах разъехались.** `nether` стоит на `f3875cd`, `sweden`
— на `d2a0d04`, боевой бридж — на ветке `worktree-stand-3xui-results`. На
поведение `remove-bridge` это не влияет, но `flock` на порталах нет ни там, ни
там.
